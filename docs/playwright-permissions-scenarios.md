# Playwright Permissions Scenarios

This report describes the executable Playwright permission coverage in `end2end/tests/permissions.spec.ts`.

The tested access model is capability + scope + ownership. Capabilities decide whether an action or surface exists, scoped role assignments limit that capability to an organization subtree, and response ownership/delegation grants access to assigned response work. The UI label "Responses" maps to the API capability family `submissions:*`.

Project directive: every new permission-controlled surface, action, or data-access path should add or update executable Playwright permission coverage when the behavior is currently testable. Each added scenario should include positive and negative assertions for the relevant capability, scope, and ownership/delegation combination, and this report should be updated in the same change.

## Fixture Accounts And Roles

The suite creates Playwright-owned fixtures with a `pw-permissions-*` prefix through admin APIs after seeding the demo dataset.

## Fixture Lifecycle

Permission fixtures are created through supported admin APIs, then the suite removes Playwright-owned records with a direct `docker compose exec postgres psql` cleanup pass before and after the run. The cleanup is intentionally limited to records with the `pw-permissions-*` prefix and dependent rows discovered from those records.

Direct SQL cleanup is a pragmatic local test harness choice until user, role, dataset, and workflow lifecycle APIs are complete. Keep fixture names prefixed with `pw-permissions-*`, and update the cleanup SQL whenever new permission fixtures create additional linked records such as dataset revisions, major-line materializations, components, dashboards, submissions, assignments, or workflow instances.

When local fixture volume gets noisy or cleanup falls out of sync with schema changes, reset the development database with `.\scripts\local-launch.ps1 -FreshData` before rerunning Playwright.

| Fixture | Role capabilities | Scope/delegation purpose |
| --- | --- | --- |
| No-access user | empty role | Verifies protected capability surfaces reject accounts with no capabilities. |
| Response owner | `submissions:read_own`, `submissions:respond` | Verifies own assignment pending/start/read and denial for another user's assignment. |
| Scoped manager | `hierarchy:read`, `forms:read`, `workflows:read`, `workflows:manage`, `submissions:read_own`, `submissions:respond`, `submissions:manage`, `operations:view`, `datasets:read`, `components:read`, `dashboards:read`, `dashboards:manage` | Verifies scoped positive and negative access from the `Demo Program Family Outreach` subtree, plus own out-of-scope response access. |
| Delegate | `submissions:read_own`, `submissions:respond` | Verifies delegated-to-self work. |
| Delegator | `submissions:read_own`, `submissions:respond` | Verifies delegated work access through `delegate_account_id`. |
| Admin | existing `admin@tessara.local` with `admin:all` | Verifies global visibility and creates fixtures. |

## Implemented Scenario Matrix

| Scenario family | Positive checks | Negative checks |
| --- | --- | --- |
| Capability absence | None; no-access user authenticates only. | No-access user receives forbidden responses from admin, forms, workflows, workflow assignment, submissions, datasets, components, and dashboards APIs. |
| Shell navigation | Scoped manager can see allowed product nav such as Forms and Responses. | Scoped manager cannot see Administration navigation. |
| Hierarchy routes | Scoped manager can load organization list/detail/edit/create routes for visible hierarchy records. | Scoped manager does not see out-of-scope nodes in the organization list and direct out-of-scope detail/edit routes do not expose editable content. |
| Forms UI visibility | Scoped manager sees an in-scope form in `/forms`. | Scoped manager does not see an out-of-scope form in the list and direct detail navigation renders the unavailable state. |
| Forms manage routes | Scoped manager can create and update a form with in-scope visibility and load create/edit routes. | Scoped manager cannot create or update a form with out-of-scope visibility and out-of-scope edit routes do not expose edit actions. |
| Role route and creation | Admin creates a role through the admin API and loads `/administration/roles`. | Non-admin administration access is covered by shell/API denial scenarios. |
| Administration routes | Admin loads users, user detail, user edit, user access alias, and node-type routes; admin creates/updates a node type through APIs. | Scoped non-admin receives forbidden responses for users, user detail/access, and node-type admin APIs. |
| Global capability | Admin reads in-scope and out-of-scope forms, datasets, components, dashboards, and workflow assignments. | Not applicable; `admin:all` is intentionally global. |
| Scoped forms | Scoped manager lists and reads forms whose visibility nodes overlap the assigned subtree. | Out-of-scope form is absent from list and direct detail access is forbidden. |
| Scoped datasets | Scoped manager lists, reads, and previews datasets whose visibility nodes overlap the assigned subtree, with preview rows limited to effective scope. | Out-of-scope dataset is absent from list and direct detail/table access is forbidden. |
| Dataset revisions | Admin and in-scope dataset managers can review draft revisions and publish them; read-only scoped users can read published revisions only. Revision history dependency summaries and revision detail dependency rows include only downstream assets visible to the caller. | Read-only scoped users and out-of-scope dataset managers cannot read or publish draft revisions; revision history omits drafts for read-only users. Out-of-scope downstream dataset, component, and dashboard names and counts are hidden from scoped readers. |
| Scoped components | Scoped manager lists and reads components backed by visible dataset major lines, can execute an in-scope component table endpoint, and can access manageable component admin routes. Public reader routes expose only published component versions while admin routes expose draft/published/superseded authoring state. | Out-of-scope component is absent from list and direct detail/table access is forbidden. Scoped component manager cannot bind a hidden Dataset major line, validate an out-of-scope binding, or publish a draft bound to an out-of-scope Dataset major line; these denials assert the stable forbidden error envelope. |
| Visual components | Sprint 4B coverage creates a published in-scope Bar component fixture backed by a visible Dataset major line, confirms scoped readers list/read it, executes `/api/components/{component_ref}/bar`, and opens the native visual viewer route. | Sprint 4B coverage creates a published hidden Bar component fixture backed by an out-of-scope Dataset major line and confirms the scoped reader cannot list, read, or execute its `/bar` endpoint. Wrong-kind and `/stat_card` route checks live in the component workflow spec. |
| Scoped dashboards | Scoped manager lists and reads Dashboards whose visibility overlaps the assigned subtree, loads native directory/detail/viewer routes, and sees an unavailable footprint when a readable Dashboard contains a hidden Component placement. | Out-of-scope Dashboard is absent from the list and direct detail access is forbidden; a redacted placement never issues a hidden Component execution request. |
| Workflow candidates and assignments | Scoped manager sees only in-scope assignment candidates, can inspect assignees for an in-scope candidate, and can start an in-scope assignment through `workflows:manage`. | Scoped manager cannot create/start out-of-scope assignment work and should not see out-of-scope workflow assignments in the assignment list. |
| Operations status | Scoped manager with `operations:view` can load `/operations` and `GET /api/operations/status` for scoped workflow assignment and dataset readiness status. | No-access users do not see Operations navigation and receive forbidden status API responses; out-of-scope datasets and workflow assignment records are excluded for scoped users. |
| Workflow manage routes | Scoped manager creates and reads an in-scope workflow and loads create/detail/edit routes. | Scoped manager cannot create/update/read out-of-scope workflows; out-of-scope routes do not expose edit actions. |
| Submissions scope plus ownership | Scoped manager can read/start an out-of-scope assignment assigned to them through ownership and can manage in-scope submissions through scope. | Scoped manager cannot read an unrelated out-of-scope submission. |
| Response ownership | Owner sees and starts their own pending assignment, reads the resulting submission, and an isolated response-editor account can load the edit route for its own draft. | Owner cannot start another user's non-delegated assignment; a different user cannot load the draft edit route. |
| Delegation | Delegator can query delegate pending work through `delegate_account_id`, start it, and read the resulting submission. | Non-delegated owner cannot access that delegated assignment. |
| Dashboard manage routes | Scoped manager can create/update an in-scope Dashboard and load the native create, detail, composition-editor, and focused-viewer routes. | Scoped manager cannot create/update Dashboards with out-of-scope visibility. |
| Session metadata | Session endpoint exposes capabilities, assigned scope roots, and delegations. | No legacy access switch is asserted or required. |

## Known Remaining Gaps

- UI-level create/edit permission checks combine route assertions with API-level action checks where form/editor interactions require a larger purpose-built fixture. Dashboard composition interactions now have dedicated browser coverage in `end2end/tests/dashboards.spec.ts`.
- There is no New User Screen yet, so user creation is verified through admin APIs rather than a browser form.
- Sprint 4A scoped asset semantics intentionally split read visibility from authoring authority. Read visibility is overlap-based: a scoped reader may list/load an asset when at least one asset visibility node overlaps their scope. Authoring, binding, publishing, and dashboard placement are containment-based: the manager's scope must fully contain every implicated visibility node for the asset and bound data sources.
- Sprint 4A component authoring coverage lives in `end2end/tests/components.spec.ts`: admin creates a thin `table` component with an atomic first draft, validates unsaved native authoring config and renders field-path findings, reviews Dataset catalog context in the authoring UI, validates table config successfully, verifies old `aggregate_table` component payloads are rejected as unsupported, publishes from the edit-screen save-and-publish menu, executes current and version-specific table endpoints with runtime search/filter/sort/pagination/visible-column controls, verifies draft-only components are absent from the public list, verifies the public reader stays on the published table while a replacement draft exists, creates a replacement version through the edit-screen consumer review modal, verifies supersede behavior, verifies superseded versions are immutable while the current published version can be explicitly updated in place, rejects draft component-version dashboard placement, proves legacy draft placements are ignored by dashboard readers, and opens the native list/detail/edit/viewer routes over a Dataset major-line binding. `crates/tessara-web-components` also covers structured publish-validation findings with field paths, Dataset catalog option labels, the native viewer query builder, saved component filters, filter operator query encoding, and checkbox column-picker behavior so visible-column state remains server-driven without relying on a raw comma-separated control.
- Sprint 4A component management permission coverage lives in `end2end/tests/permissions.spec.ts`: a scoped component manager can reach manageable component admin routes and native in-scope component detail/viewer routes, but cannot bind a guessed out-of-scope Dataset major line, validate an out-of-scope binding, publish an out-of-scope draft created by an admin, or direct-load hidden component detail/viewer routes. The out-of-scope bind, validate, and publish denials assert a stable `forbidden` error body mentioning the missing `components:manage` scope.
- Sprint 4A backend major-line component coverage lives in `crates/tessara-api/tests/demo_flow.rs`: a component bound to Dataset v1 renders the expanded v1 major-line surface after a compatible v1 publish and remains pinned to v1 after Dataset v2 publishes. The same lifecycle test also verifies concurrent draft writes converge on one working draft while the published version stays current, working drafts do not inflate Dataset dependency counts, concurrent publish attempts leave exactly one published version and no draft, marks the v1 major-line materialization as failed, and clears it before publishing a new component version, proving publish validates the binding/config contract independently from cache readiness and that render returns stable `materialization_state = failed` and `pending` table responses.
- Future component coverage should add fuller browser-native authoring interactions for optional search fields, display-label overrides, and any richer table viewer affordances once those controls are promoted beyond the first thin-table pass.
- Sprint 4B added first-class visual component kinds and native viewers. Playwright coverage verifies UI-driven authoring and publish/view flows for Bar, Line, Pie, Donut, and StatCard, visual validation, no `/bridge/*` requests during the visual viewer path, and scoped Bar component visibility/forbidden behavior. At closeout, the full 41-test browser suite and `validate-e2e.ps1` passed against the fresh squashed-baseline Sprint 4B stack at `http://127.0.0.1:8080`.
- Sprint 5A Dashboard coverage lives in `end2end/tests/dashboards.spec.ts` and `end2end/tests/permissions.spec.ts`: it loads all five native Dashboard routes, proves directory/create/detail/editor loads stay metadata-only, exercises add/direct move/resize/remove/save/dirty preview behavior, verifies selected and focused viewers execute exact pinned versions, checks narrow stacked reading order without horizontal overflow, and proves a redacted placement preserves its footprint without executing the hidden Component.
