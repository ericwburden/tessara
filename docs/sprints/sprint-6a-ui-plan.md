## Approved Product Contract

### Groups

- `core.main` and `core.admin` are Core-required stable group identities.
- Main and Admin cannot be deleted. They and all custom groups have persisted dense display order.
- Effective global `modules:manage_navigation` may create, rename, reorder, and delete custom groups at runtime.
- A group containing any item cannot be deleted until its items are moved.
- Custom group IDs are immutable opaque `custom.<lowercase UUID v4>` values generated by the manager client and validated by the server; `core.*` is reserved.
- Group labels are trimmed, 1–64 Unicode scalar values, contain no control characters, and are case-insensitively unique within an installation. Renaming changes only the label.
- Custom-group labels are configurable and required. Editing the display labels of Main/Admin is supported by the model but is not an exit-critical requirement.
- Management readback includes empty groups. Actor shell projections omit groups with no eligible visible items. Home ensures an authenticated shell always has Main.

### Built-In Core Destinations

Protection is expressed as independent flags rather than one overloaded “fixed” state.

| Stable destination | Route | Default group | Remove | Hide globally | Move between groups | Reorder in group | Actor eligibility |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `core.home` | `/` | `core.main` | No | No | No | Yes | Authenticated shell |
| `core.organization` | `/organization` | `core.main` | No | Yes | No | Yes | Existing hierarchy read/manage rules |
| `core.admin.users` | `/administration/users` | `core.admin` | No | No | No | Yes | Existing `admin:all` rule |
| `core.admin.roles` | `/administration/roles` | `core.admin` | No | No | No | Yes | Existing `admin:all` rule |
| `core.admin.node_types` | `/administration/node-types` | `core.admin` | No | No | No | Yes | Existing `admin:all` rule |
| `core.admin.modules` | `/administration/modules` | `core.admin` | No | No | No | Yes | Effective global `modules:read` |
| `core.operations` | `/operations` | Pending optional default | No while route exists | Yes | Yes | Yes | Existing `operations:view` rule |

Operations remains Core-owned but is not protected because Home is expected to subsume it. It remains a live route and optional destination until a later explicit retirement decision.

### Optional Destinations

- Forms, Workflows, Responses, Operations, Datasets, Components, Dashboards, and future eligible module contributions are optional navigation destinations.
- Every optional destination appears exactly once in the installation policy, assigned to exactly one group, even when hidden.
- Managers may show/hide, move between any groups, and reorder optional destinations freely.
- Module availability and actor capability filtering remain independent final rendering conditions.
- Showing a destination never grants access; hiding it never revokes direct-route or API authority.
- Module manifests/catalog entries may provide default-placement hints, but Core policy owns the persisted final placement.

### Administration Route Removal

- Remove the Administration navigation destination and `AdministrationPage`.
- Remove the `/administration` route completely. It has no compatibility handler or application tombstone and falls through to the ordinary unmatched Axum 404 response, with no `Location` header or redirect.
- Preserve `/administration/users`, user detail/edit/access, `/administration/roles`, `/administration/node-types`, `/administration/modules`, and module detail with their current authorization and SSR ownership.
- Give each direct Core Admin destination its own active navigation key so descendant routes highlight the correct item.
- Datasets and Components remain available through their own destinations; they are not Core Admin requirements merely because the removed page linked to them.

## Decision Gate 1: Initial Optional Placement

Before schema fixtures, migration mapping, or navigation-composer mockups are frozen, approve one initial group layout for optional destinations. The implementation must not invent a third seeded group or silently move Datasets without this decision.

The safe choices are:

1. seed only Main/Admin and place every optional destination in Main initially; or
2. seed an additional configurable product/data group and name the exact destinations assigned to it.

Recommended default: choose option 1. It keeps Admin Core-only, avoids inventing a product taxonomy, and still lets a navigation manager introduce custom groups. The deterministic candidate order is:

- Main: Home, Organization, Forms, Workflows, Responses, Operations, Datasets, Components, Dashboards.
- Admin: User Management, Roles & Access, Node Types, Module Management.

Existing installations migrate to the approved initial layout while preserving relative order and visibility wherever that mapping is unambiguous. New installations receive the same deterministic layout.

Gate approval also freezes the Core-catalog defaults for the six current module contributions. A later software release may introduce another recognized optional destination only with an explicit Core-catalog default that references a required group; reconciliation appends it once using its catalog visibility default and records a system audit. Custom groups are never catalog defaults because administrators may delete them. Missing or invalid catalog defaults fail closed without partially changing policy. Legacy descriptor group/band fields remain immutable discovery hints and never overwrite effective installation placement.

## Core Catalog Versus Configured Composition

Core may and should hard-code the authoritative built-in catalog, but not the rendered grouping or order.

The built-in catalog owns:

- stable destination identity, current route, label, owner, capability predicate, default placement, and protection flags;
- stable `core.main` and `core.admin` group identities and default labels;
- collision prevention between Core and contributed IDs/routes; and
- fail-closed fallback definitions.

Installation policy owns:

- group instances, display labels, and group order;
- one placement, visibility value, and item order for every known destination; and
- the monotonic policy revision.

The server composes and capability-filters the actor-specific shell projection. Desktop and mobile renderers consume the same ordered projection and do not reproduce policy rules.

6. retain the existing policy revision because the conversion preserves semantic configuration, and insert exactly one system `navigation_policy_schema_migrated` audit event containing from/to schema versions plus old/new policy fingerprints;
7. make a rerun a no-op or fail with an exact integrity code rather than duplicating state;
8. retain `module_navigation_contributions.group_name` and `reorder_band` unchanged as frozen descriptor/catalog provenance during Sprint 6A-UI, but remove them from effective policy reads, writes, and shell composition; and
9. prove fresh creation, populated Sprint 6A upgrade, interrupted/atomic failure, backup/restore, and rollback-package compatibility; and

Fresh reconciliation creates the deterministic policy once and records a system initialization audit. Subsequent reconciliation preserves every valid administrator group/order/visibility choice. A newly recognized catalog destination is appended once under the rule frozen above. A required group or placement missing from an already-current catalog/policy is corruption: startup fails closed with an exact integrity code rather than silently repairing or resetting policy.

## Versioned API And Shell Contract

The current v1 policy wire exposes `immutable_core_items`, contribution groups, reorder bands, and before/after anchors. It cannot represent the approved model and must be intentionally superseded by a group-aware version.

The existing management endpoint and shell bootstrap advance to an explicit group-aware schema v2. Unknown or malformed schema versions fail closed. The v2 management response must expose:

- installation ID, schema version, current revision, and `can_manage_navigation`;
- ordered groups with stable ID, label, order, Core/custom ownership, and allowed operations;
- every Core and contributed destination with stable ID, label, route/destination, owner, group ID, visibility, order, eligibility metadata, availability, and allowed operations; and
- explicit unavailable/integrity states.

Mutation remains one atomic expected-revision update covering the complete group and placement collection. It validates:

- non-negative revision and dense unique group/item order;
- stable required group identities;
- complete exact destination membership;
- one placement per destination and valid group references;
- protected removal, hiding, and group-lock rules;
- non-empty group deletion rejection;
- identifier, label, route, ownership, and Core-collision rules; and
- optimistic concurrency with no partial writes.

The group-aware shell projection accepts arbitrary valid ordered groups. Client validation must no longer require exactly Main then Admin or hard-coded contribution ranks. It still validates schema, identifiers, uniqueness, same-origin paths, ownership shape, group references, required Core invariants, and absence of contribution leakage in a fail-closed response.

Authorization remains unchanged:

- effective global `modules:read` reads the policy and Module Management;
- effective global `modules:manage_navigation` implies read and alone enables mutation;
- effective `admin:all` implies both global module capabilities and remains the sole universal-sentinel mixed-scope exception;
- policy does not mutate roles, capabilities, route guards, module availability, or API authorization.

## UI And UX Contract

### Navigation Composer

The existing band table is replaced, not relabeled.

Reader mode shows:

- ordered groups and their labels;
- protected versus custom group status;
- ordered destinations, ownership, route, visibility, and actor-independent placement;
- why protected controls are unavailable; and
- explicit copy that display configuration does not grant access.

Manager mode additionally supports:

- create and rename custom group;
- reorder all groups;
- delete an empty custom group;

## Risks And Abort Rules

| Risk | Prevention | Response |
| --- | --- | --- |
| Seed resets administrator choices | Idempotent reconciliation tests with customized policies | Block release; never repair by overwriting valid configuration. |
| Incomplete migration | Exact membership/fingerprint and atomic failure proof | Roll back transaction and restore the pre-upgrade backup. |
| Navigation grants access | Independent capability/route/API tests | Treat as a security defect; stop rollout. |
| Required destination becomes unreachable | Protection matrix plus actor-specific shell tests | Fail the mutation atomically and preserve prior revision. |
| Arbitrary groups break shell hydration | Versioned projection validation and desktop/mobile/no-JS tests | Fail closed to Core fallback and correct the projection. |
| Test rewrite weakens parity | Mandatory pre-edit rows and diff reconciliation | Reject the change until equal-or-stronger proof exists. |
| UI model depends on drag | Explicit keyboard move/group actions | Block acceptance until all operations are non-drag accessible. |
| Scope expands into runtime modules | Explicit non-goals and diff review | Defer to Sprint 6B or later roadmap work. |
