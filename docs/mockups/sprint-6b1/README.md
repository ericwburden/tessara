# Sprint 6B1 HTML/CSS Module Management Suite

Status: coordinated review suite approved on 2026-07-22. These runnable HTML documents record bounded Sprint 6B1 changes; they are not 1:1 reproductions of the application and are not wholesale implementation specifications.

## Brief

- Product surface: Core-owned Module Management at `/administration/modules`.
- Primary user: an installation operator with global module read access.
- Primary outcome: understand what is deployed, whether it is healthy, and what operator action is safe next.
- Visual source: the completed Sprint 6A-UI application shell, production stylesheet, and approved structured-registry hierarchy.
- Constraints: native semantic HTML, only minimal review-only JavaScript needed to demonstrate established tab behavior, no image-generated UI, one strong action per state, and no container-control authority in the browser. Mockup-only class names, simplified assets, and omitted established UI are not production requirements.

These are complementary screens in one product flow, not alternatives. A and B propose bounded updates to approved Sprint 6A-UI surfaces; C proposes the new Deployment screen. All pages load `target/site/pkg/tessara-web.css`, generated by the existing `npm run tailwind:build`, plus [prototype.css](./prototype.css) for review-only layout rules. Their application-like presentation helps evaluate a proposed delta in context; it does not make every rendered detail part of that delta.

## Implementation Boundary

- The current application is the authoritative baseline for existing layout, components, icons, copy, interactions, accessibility behavior, responsive behavior, and approved functionality.
- The mockups authorize no application change by themselves. Only additions or modifications explicitly discussed during refinement, recorded below, and subsequently approved may enter implementation scope.
- Everything outside an approved delta must remain unchanged. A missing, simplified, or approximate mockup element must never be interpreted as an instruction to remove or replace its production counterpart. This includes the many application icons that these HTML files do not reproduce.
- Before implementation, compare each affected production screen with its mockup and produce a bounded change list. Review and test the resulting application as the existing screen plus those changes, not as a recreation of the HTML file.
- Mockup markup, DOM hierarchy, class names, spacing, and asset substitutions are illustrative unless a refinement decision explicitly identifies one of them as the desired application change.

## Approved Screen B Refinement Record

Screen B received explicit whole-screen approval on 2026-07-22. Its bounded application delta is:

- `View deployment receipt` links to Screen C and uses the same icon-bearing secondary-action treatment as `View source descriptor (JSON)`.
- Keep the existing header identity treatment for the canonical Definition ID; do not duplicate Module Instance in the header.
- Add `Independently deployed` and `Healthy and enabled` to the existing header badge set, with explanatory tooltips for every badge variant.
- Add Descriptor configuration schema and Module Release readback to the Definition panel.
- Keep Module Instance in the Definition panel with its own copy action.
- Add the `Ready` lifecycle badge and the Instance continuity, Deployment, Application, and Data assessment dimensions. Badge variants require explanatory tooltips.
- Use `Instance continuity` for durable-instance state and `Artifact provenance` for manifest, runtime-image, publisher, and curated-release source; avoid the ambiguous repeated `Identity` label.
- Add copy actions beside displayed manifest, runtime-image, and instance identifiers.
- Add Artifact provenance readback for the manifest, runtime image, publisher, and curated-release source; size the panel to its content rather than stretching it to match the adjacent column. Do not imply cryptographic verification in Sprint 6B1.
- Add Configuration as a functional, dedicated tab view. Keep Diagnostics on Overview and do not add a Diagnostics tab. Preserve every established detail tab and its live-application behavior.
- Present Configuration as read-only observed state. The healthy state shows the validated release and `Configuration findings: None`; it does not show a review badge.
- Reserve configuration warning treatment for actual findings such as a missing or invalid value, release/schema incompatibility, desired-versus-applied drift, or validation that is unavailable or stale. Replace vague `Review suggested` copy with a concrete state such as `Needs attention` or `Cannot verify`.
- When a configuration finding exists, show its stable code/path/message, operational impact, last observation, and the supported resolution destination. Link to the module-owned configuration screen when the manifest supplies that semantic destination; otherwise identify the external owner/workflow without presenting a dead mutation control. Keep configuration findings distinct from dependency, readiness, and health findings.
- Remove the explanatory Configuration and Diagnostics messages, the undefined `Review configuration` button, and the duplicative Operator actions panel.
- Use the live module-detail panel heading treatment consistently and preserve the live application's equal-width detail columns.
- Use spacing between diagnostics badges and their health-check routes.

No review-flagged Screen B candidates remain. Only the recorded additions and changes above are authorized; all other live module-detail UI remains unchanged.

Screen B uses review-only blue flags to identify proposed additions and changes: dark surfaces use a dark-blue flag and light surfaces use a light-blue flag. The flags are review scaffolding only and must not be implemented in the application.
