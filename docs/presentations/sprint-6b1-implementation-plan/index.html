Sprint 6B1 is the point where Tessara's modular architecture becomes an operated runtime. This briefing explains the outcome, the approved product scope, the workstreams, the evidence gates, and the release decision.

6B1 turns modular architecture into an operable runtime

Executive outcome

Validate and apply a signed, single-host container deployment; route to one independently deployed reference module; observe it without making Core a container control plane.

The sprint closes only when deployment, containment, recovery, upgrade, and rollback work end to end.

Deploy with trust

Verify digest-pinned OCI artifacts and publisher identity before Docker Compose mutates the installation.

Operate with containment

Use same-origin routing and Core-rendered fallback so a failed module never takes Core down with it.

Explain what changed

Persist exact releases, instances, health dimensions, and sanitized receipts for operator readback.

2
The implementation has three executive outcomes. Trust is established before mutation. Runtime failures remain contained. Operators can see the exact applied state and supporting evidence.

These screens are complementary, not alternatives. A and B are bounded additions to approved application screens. C is the new deployment view. The live application remains the authoritative baseline; mockup omissions do not authorize removal.

Four workstreams deliver the capability without creating a new control plane

Build outside-in

Start with verifiable contracts and operator-owned execution, then expose only supported readback in Core.

Each workstream is independently testable; integration proceeds only when its upstream contract is stable.

01

Deployment contract · tessara-oci-v1, signed manifests, stable findings, sanitized receipts

02

Local execution · thin tessara-deploy over installed Compose and Cosign; idempotent apply and rollback

03

Runtime platform · Traefik routing; one PostgreSQL cluster; isolated databases, owners, and roles

04

Reference proof + UI · Scoped Records module, Core read model, and approved A/B/C deltas

4
The work is intentionally outside-in. We establish a portable declaration and reliable evidence first, then operator-owned execution, then the runtime platform, and finally the reference module and Core readback. Testing runs within each workstream and at their integration boundaries.

Delivery advances through evidence gates—not UI completion alone

GATE 1

Contracts & persistence

Freeze declaration, finding, receipt, installation-identity, and database boundaries. Prove deterministic validate and plan.

GATES 2–3

Materialize & contain

Apply signed artifacts through Compose; migrate, health-gate, route, stop, fall back, and restore.

GATES 4–5

Expose & prove

Persist readback; implement approved A/B/C deltas; execute upgrade, rollback, responsive review, and conformance.

5
There are no speculative calendar dates in this plan. Progress is gated by evidence. The UI cannot outrun the contracts it explains, and the sprint cannot close on screenshots alone.

The largest risks are controlled by explicit ownership boundaries

Hard boundaries

No custom scheduler. No Docker socket in Core or the browser. No cross-database shortcuts.

The approved mockups authorize bounded deltas—not a rewrite of the existing application.

01

Scope drift · Treat each approved screen record as the implementation contract; preserve everything else

02

Authority leakage · Only tessara-deploy and the host operator mutate deployment; Core and UI read status

03

Irrecoverable apply · Bind receipt, plan digest, expiry, idempotency, confirmation, backup, and rollback

04

State ambiguity · Keep trust, compatibility, identity, deployment, config, readiness, and health separate

6
The risk posture comes from ownership. Compose owns lifecycle, Traefik owns routing, Cosign owns signature verification, PostgreSQL owns durable state, and tessara-deploy owns operator mutation. Core explains status without becoming the control plane.

The sprint is done only when the operator completes the full recovery loop

One signed fixture. One origin. One auditable receipt chain.

Demo the path: validate → plan → apply → observe → stop module → inspect fallback and diagnostics → restore → compatible upgrade → rollback.

Acceptance also proves one PostgreSQL container with separate Core, deployment-control, and Module Instance databases—and prohibited cross-database access fails.

Exact artifacts verified before mutation
Core remains reachable during module failure
Identity and data survive upgrade and rollback
Screens A, B, and C match approved deltas
All workflows pass without skipped proof
7
The executive release decision is simple: approve completion only when this loop works with the signed fixture and the UI shows the supported evidence. The immediate next step is Gate 1—freeze the contracts and persistence boundaries.
